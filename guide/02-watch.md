# 조심할 것

6개월 안에 가장 먼저 올 신호는 셋입니다. **접수 → 리드 전달 2일 초과**, **리뷰어가 빈 PR**, **서브 구현 커밋 0**. 앞의 하나는 [오늘](#today) 타일이 자동으로 세고, 뒤의 둘은 금요 읽기 때 직접 봅니다.

예방 장치는 종이 네 장과 표 한 장입니다. 접수 양식 7칸과 S/M/L 분류, [결정 경계](#bounds) 1쪽, 서브 최소 의무 한 줄, 장애 1차·2차 표, 그리고 사이클마다 쓰는 [자리 계산](#programs). 모두 [양식과 문장](#guide/templates)에 있습니다. 새 회의는 만들지 않고, 이미 있는 주간 서면 보고·격주 팀장 1:1·매월 첫 주 리스크 15분·3개월 점검·6개월 재검토에 끼워 넣습니다.

## 실패 시나리오 14개

괄호 안은 [수첩](#notebook) 리스크 표에서 같이 보는 행의 이름입니다.

| 시나리오 | 조기 신호 | 예방·대응 |
|---|---|---|
| 1. 관리자 창구 병목(관리자 과부하의 앞 신호) | 전달 2일 초과가 주 2건 이상. 요청자가 '확인하셨나요'라고 다시 물음. 19시 이후에 접수함을 정리함 | 사람이 지키는 약속은 '리드 전달 근무일 2일' 하나만 둡니다. 단순 기술 문의는 접수함이 아니라 그 프로그램 리드의 문의 창구로 보냅니다 |
| 2. 리드 부재로 프로그램이 멈춤(리드 부재) | 서브 혼자 배포한 기록 0. 리드만 아는 설정. 리허설 중 리드에게 연락할 일이 생김 | 3~4개월 차에 리드 없이 1~2일 미니 리허설을 활성 프로그램마다 합니다. 분기 1회 서브 혼자 배포. '혼자 돌리는 데 필요한 것' 1쪽. 안 되면 문서로 메우고 3개월 더 봅니다 |
| 3. 서브가 이름뿐, 리드가 서브를 들이지 않음(서브가 이름뿐) | 리뷰어가 빈 PR, 셀프 병합. 서브 구현 커밋 0이 두 사이클. 데모에서 서브가 설명을 못 함. 인터페이스 합의 지연, 리뷰 요청 무응답 | 서브 최소 의무 한 줄(리뷰·회귀·장애 2차·분기 1회 혼자 배포). 서브 구현 자리 1~2개를 사이클마다 돌립니다. 리뷰 기한 근무일 2일, 넘기면 막힘으로 올립니다(배정 문제). 서브 범위는 리드가 정하고 인터페이스로 나눕니다. 안 되면 관리자가 리뷰어로 들어가되 관리자 시간과 맞바꾼다는 것을 압니다 |
| 4. 그림자 요청(접수함을 거치지 않은 일) | 진행 지도에 없는 일이 데모에 나옴. 이월이 특정 프로그램에 몰림. 기술 문의가 한 사람에게만 몰림 | 팀 밖 공지 1쪽: 개발 요청은 접수함, 기술 문의는 문의 창구, 긴급만 예외. 개발자가 대신 올려도 됩니다. 벌하지 않습니다. 조기 신호 '진행 지도 밖 일'을 켭니다 |
| 5. 작은 요청까지 관리자를 거쳐 느려짐 | 접수함 절반이 반나절 일. 되묻지 않고 그대로 넘김 | S/M/L 분류. S는 10분 안에 바로 전달. 리드가 직접 받은 S는 사후 등록 |
| 6. 결정 경계 충돌 | 같은 주제가 결정 로그에 결정자가 다르게 두 번. 관리자가 PR에 설계 코멘트를 닮. 리드가 위임한 모듈 설계를 통째로 다시 함. 숙련자 서브의 리뷰 반대가 주니어 리드의 결정을 대신함 | [결정 경계](#bounds) 1쪽 + '주니어 리드 프로그램의 경계는 지침의 제약 칸' 한 줄. 서브의 반대는 의견이고 리드가 이유와 함께 답해 기록합니다. 관리자가 뒤집는 조건은 넷뿐(요구사항 위반·큰 일정 영향·다른 파트 영향·안전·품질), 1:1에서 |
| 7. 자리가 넘쳐 집중이 깨짐(숙련자 병목, 주니어 과부하) | '다른 프로그램 일 때문에'. 리뷰·일정 지연, 지친 기색. 다른 업무를 겸하는 사람의 일이 밀림. 한 사람 활성 자리 3개 | [자리 계산](#programs)(1인 활성 자리 ≤ 2). 숙련자는 활성 리드 2개까지(교육·연동이 몰린 주는 1개), 서브 자리는 대기 프로그램 위주. 다른 업무를 겸하는 사람은 요일 고정·활성 자리 1·기한 대신 범위 축소. 이미 2자리인 사람에게 리드 자리를 더 주지 않습니다. 활성 7개면 누군가 3개가 되는 대신 하나를 대기로 돌립니다. 관리자가 직접 맡는 안은 흡수 금지와 부딪히므로 팀장과 정합니다 |
| 8. 리드 추정 없이 날짜 약속, 요청자 압박(요청자 압박) | 리드가 날짜를 되물음. 이월 사유가 '처음부터 무리'. '일정상 여유가 없다'는 말, 담당 지정 지연 | 2주 이내도 리드 추정 뒤에 약속합니다. 2주 초과·거절은 팀장 결재. 팀장을 거쳐 온 건은 '팀장 지시'로 표시하고, 추정과 다르면 바로 보고합니다 |
| 9. 장애 2차·야간·배포 결재가 정해지지 않음 | 장애 첫 10분이 '누구 담당이냐'로 지나감. 서브에게 운영 권한이 없음 | 1차는 그 프로그램 리드의 기술 판단, 관리자는 대외 소통·인력 조정. 2차는 서브(가정). 야간 대응과 결재는 팀에서 정합니다. 리드와 서브가 같은 날 비면 당번 1인 |
| 10. 관리자 과부하(관리자 과부하) | 본인 사정으로 1:1 취소가 이어짐. 리뷰 대기·야근 증가. 막힘 기한을 못 지킨 것이 2건 이상. 주말에 접수함 | 1:1 고정. 월 1회 시간 배분 점검. 넘긴 일을 다시 가져오지 않기. 첫 2주 시간 일지, 접수가 주 3시간 넘으면 S 직결 범위를 넓힙니다. 빈 자리를 관리자가 메우지 않습니다(흡수와 같음). 통합 설계·멘토링을 줄이려면 팀장과 다시 이야기합니다. 안 되면 팀장에게 일찍 알립니다 |
| 11. 새 자리에서 정체(새 자리 적응) | 빌드·실행이 4주 넘게 제자리. 리드에게 질문을 못 함 | 관리자가 질문 창구(멘토). 주 1회 15분. 막힌 지점을 가이드 소재로 남깁니다. 3개월 점검에서 자리를 바꿀 수 있습니다(예정된 점검이지 실패가 아닙니다) |
| 12. 주니어 사이 리드 자리 불균형(주니어 과부하·공정성) | 의욕 저하, 서로 비교하는 말 | 주니어는 모두 리드 1개 + 모듈 설계. 금요 데모에서 격주로 고르게 발표. 팀장 앞 발표 기회 |
| 13. 통합시험 같은 피크 | 긴급 대응에 전원이 들어감 | 피크를 사이클 계획에 미리 넣고 활성 수를 줄입니다. 피크 중에도 1:1·리뷰는 최소로 유지. 피크를 배움의 기회로 씁니다 |
| 14. 접수함이 쌓임 | 답 없는 요청. 두 사이클 넘긴 대기 요청 | 명확화 답이 근무일 10일 없으면 '보류'. 보류가 두 사이클 지나면 종료 안내 뒤 닫습니다. [오늘](#today)의 '지금 손댈 것'이 제안합니다 |

## 매번 챙길 목록

### 접수 때(건마다) — [접수함](#intake)

- 양식 7칸: 원문 · 무엇 · 왜·누가 결정 · 어느 프로그램 · 언제까지와 이유 · 확인 방법 · 긴급 여부. 요청자에게는 앞 5칸만 받습니다. 빈칸만 되묻습니다.
- S/M/L 분류. 긴급은 그 프로그램 리드에게 바로, 관리자는 알림만 받습니다. 단순 기술 문의는 문의 창구로.
- 날짜는 리드 추정 뒤에만. 2주 이내 약속·축소·교환은 바로, 거절·2주 초과는 팀장 결재 뒤.
- 넘길 때 세 칸: 결정된 것 / 열린 것 / 요청자. 다른 프로그램에 걸치면 그쪽 리드도 참조.
- 지표는 하나: 전달 2일 초과 건수.

### 매주 금요일 — [금요일](#friday)

- 금요 읽기 시간 안에서: '정리 중' 2일 초과 건, 진행 지도의 위험·결정 필요 칸, 진행 지도 밖 일 1분.
- [오늘](#today)의 조기 신호 6개(건 단위): 전달 2일 초과 · 막힘 시계 넘김 · 상태를 물어야 했던 순간 · 활성 자리 3개 이상인 사람 · 리뷰어 빈 PR · 진행 지도 밖 일. 둘 이상 켜지면 위 표에서 해당 행의 장치를 다시 봅니다.
- 흡수 건수 한 줄(관리자가 직접 처리한 요청 수).
- 보고 내용은 진행 지도 두 칸 + 접수 현황 + 흡수 건수. 리스크는 바로 알립니다. 개인 데이터는 넣지 않습니다.

### 격주 — 팀장 1:1

- 2주 초과 약속·거절 결재, 교환 제안 결과, '둘 다 하라'는 지시가 있었다면 그 기록.

### 매월 첫 주 — 리스크 15분 — [수첩](#notebook)

- 리스크 표의 수준을 고르고 '이번 달 점검함'을 누릅니다. 위 14행 중 이번 달에 신호가 있던 것을 메모에 한 줄.
- 기술 동기화가 있다면 결정 경계 1쪽·긴급 기준을 다시 확인하고, 다른 파트에 영향을 주는 설계를 합의합니다.
- 시간 일지로 관리자 시간 배분을 점검합니다.

### 사이클 시작(6주마다, 2~4시간) — [프로그램·자리](#programs)

- 자리 계산: 사람별 활성 자리(리드 + 서브 구현) ≤ 2. 활성 6~7개면 '이번 사이클 서브 구현' 프로그램 1~2개를 고르고 사이클마다 돌립니다.
- 프로그램 표(시스템·리드·서브·활성/대기·서브 구현 여부)를 고칩니다. 같이 보는 표에는 사람별 합계가 없습니다.
- 활성 프로그램마다 지침 네 칸: 문제 · 성공 기준 · 제약 · 빼는 것. '어떻게'는 쓰지 않습니다. 통합 설계가 걸린 프로그램은 지침과 설계안을 따로 적습니다.
- 자리를 비울 예정이면 당번 1인과 복귀일을 알립니다.

### 3개월 점검

- 서브 혼자 배포가 한 번이라도 됐는지, 서브 구현 자리가 실제로 돌았는지.
- 자리 쏠림(활성 자리 3개)은 먼저 재배정. 재배정으로도 안 되거나 인원이 줄었으면 묶기·동결.
- '둘 다 하라'가 3번 쌓였으면 용량을 다시 이야기합니다.
- 새 자리에 적응 중인 사람의 자리를 계속할지 정합니다. 3~4개월 차 미니 리허설.

### 6개월 재검토

- 프로그램 리드 체계를 유지할지.
- 활성 수와 서브 구현 비율.
- 리드가 길게 자리를 비웠을 때 서브 혼자 지원이 됐는지.
- 익명 서면 회고 한 줄: '누가 결정하는지 몰랐던 순간'.

## 근거

시나리오와 예방 장치는 앞선 시뮬레이션과 역할극에서 나온 **시뮬레이션 기반 가설**입니다. 관리자 자원이 바닥나면 리더 행동이 나빠진다는 것, 밀착 감시와 상태 보고가 스트레스를 올린다는 것은 문헌에서 **방향만** 빌렸습니다. 수치는 이 팀에 옮기지 않았습니다.
